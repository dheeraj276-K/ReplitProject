# MASTER PROMPT — SMART TOKEN GENERATION FULL-STACK WEB APPLICATION

Act as a **senior full-stack software engineer, UI/UX designer, database architect, security engineer, and DevOps engineer**.

Build a complete, production-ready full-stack web application called:

# SmartQueue — Digital Token Generation & Queue Management System

## 1. PROJECT PURPOSE

Build a web application that allows users to generate a digital queue/token remotely instead of physically waiting in a long queue.

The core idea:

**User → Login/Register → Select Service → Enter Required Information → Generate Token → View Queue Status → Track Estimated Waiting Time**

The application should reduce unnecessary physical waiting by allowing users to obtain a token before reaching the location.

The application must be designed so that it can later be used by hospitals, clinics, government offices, college offices, restaurants, banks, service centers, and other organizations.

# 10. TOKEN GENERATION LOGIC

Implement proper queue logic.

When a user requests a token:

1. Verify authentication.
2. Verify the selected service exists.
3. Verify the service is active.
4. Check whether the user already has an active token for that service.
5. Determine the next available token number.
6. Create the token.
7. Assign queue position.
8. Calculate estimated waiting time.
9. Return token information.

Example response:

{
  "token": "G025",
  "service": "General Consultation",
  "queuePosition": 8,
  "estimatedWaitTime": 24,
  "status": "WAITING"
}

# 23. DATABASE FUNCTIONS / TRANSACTIONS

Token generation must be concurrency-safe.

If two users request a token at exactly the same time, they must receive different token numbers.

Use PostgreSQL functions, transactions, sequences, or another reliable atomic mechanism.

Avoid:

SELECT MAX(token_number) + 1

as the only mechanism because it can create duplicate tokens under concurrent requests.
